# 2026-08-16 -- umbrella 8756070: 9h13m, first real stage-2 dolmino steps, killed by an unexplained PBS -14

> Last updated: 2026-08-23

**TL;DR** -- the ~2k-node umbrella took **six PBS seat attempts** to start, then
ran 9h13m of a 24h allocation and was **terminated externally** with
`Exit_status = -14` while all three live trainers were mid-stride. Three of five
chains advanced and checkpointed cleanly; the two constant-LR forks died on a
one-word bug in their pinned clone. **The headline result is t0**: the first
3,312 steps of 2B stage-2 continued pre-training on pure dolmino-mix-1124, warm
started from the completed 4.674T endpoint, descending cleanly with no sign of
the divergence that killed the previous dolmino attempt.

## The headline: stage-2 dolmino is not diverging

This was the first production run of the 2B stage-2 recipe, mirroring MDS
`train_aGPT_2B_sophiag_stage2.sh`: pure `dolmino-mix-1124`, LR 2.17e-5,
`LR_DECAY_STYLE=constant`, sophiag, warm started from the finished stage-1
endpoint `step-46429`.

**The warm start is confirmed, not assumed.** Step 1 logged loss **2.6004**; a
random init starts near 12.98. Stage 1 finished at 2.68687, so stage 2 opened
slightly *better* than stage 1 ended -- consistent with moving from olmo-mix to
a cleaner mix. Flags verified in the launch line:

```
--checkpoint.initial-load-path=.../agpt-2b-sophiag-olmo-mix-1124-n512-gbs12288/step-46429
--checkpoint.folder=checkpoints/agpt-2b-stage2-dolmino-n512-gbs12288
--dataloader.dataset-path=.../dolmino-mix-1124.txt
--lr-scheduler.decay-ratio=0.0  --lr-scheduler.min-lr-factor=1.0
```

Note `initial_load_model_only: true` -- **optimizer moments do NOT carry over**,
so sophiag restarts its Hessian estimate. MDS did the same and constant LR makes
it defensible, but it is a real discontinuity, not a seamless resume.

**Why a new checkpoint dir rather than continuing the old one:** stage 1 is
*finished* (46,429/46,429, zero budget left). Resuming into it would exit
immediately, interleave dolmino checkpoints into olmo-mix step numbering, and
put the pristine 4.674T endpoint at risk. `initial_load` for weights plus a
fresh step counter is the same pattern MDS used.

### It did not reach the falsification point

The 2026-07-18 attempt (`8663177`) NaN-diverged at **step 3,801**. t0 reached
**3,312** -- about 500 steps short. So the decisive test is still open.

What we can say: 3,312 clean steps on pure dolmino at LR 2.17e-5, loss
descending 2.6004 -> 2.5435, grad norm steady around 0.47-0.53, contradicts the
idea that dolmino destabilises this model quickly. It does not yet rule out a
step-3801-class event. **Next run should be watched through ~4,000.**

That earlier attempt also used a different recipe -- olmo50/dolmino50 at LR
2e-6, one TENTH of this LR -- so its LR was never the plausible cause; it looked
like a single-step overflow on a dolmino batch.

## Why it ended: an external kill we cannot explain

`Exit_status = -14` at 09:13:43 of a 24:00:00 allocation. No error, no signal
message, no traceback on any slot; the umbrella's own log ends at
`all 5 trainers launched; waiting...` with no stop line; no `.e` file was
produced at all. The script was terminated from outside.

Excluded by direct check -- head node `x4305c0s2b0n0` healthy and already
reassigned to another job; allocation at 1,429,777 node-hours; `large` queue
`enabled/started = True`; no NaN/OOM/CCL anywhere in the logs; the only
reservations are Mon and Wed. PBS exposes no user-visible record of who issued
the kill.

Full write-up and draft ALCF ticket:
[`known-bugs/aurora-job-8756070-exit-14.md`](../../../../reference/known-bugs/aurora-job-8756070-exit-14.md).

## Six seat rejections before it ran

```
comment  = Not Running: PBS Error: Execution server rejected request
run_count = 6
```

Each attempt drew the same `x4305c0s*` rack whose lead node was offline with
`EXECJOB_BEGIN: skipped execjob_end found via tmpfs check; reboot required`.

**Correction to a reading made during the run:** this was first taken as our job
offlining one node per attempt -- cumulative damage. It is not. Only that single
node names `8756070`; 13 other `reboot required` nodes at the same moment
belonged to nine other users' jobs. A cluster-wide condition, with PBS
repeatedly selecting a set whose lead node was already sick.

## Our own two bugs

**1. `AttributeError: 'Config' object has no attribute 'job'` killed t3/t4.**
Every rank, at `trainer.py:671`:

```python
dump_folder=config.job.dump_folder,     # constlr clone -- WRONG
dump_folder=config.dump_folder,         # the other three clones, line 238
```

The `agpt-2b-constlr-from9200` clone (pinned at `f319e3fa`, predating the
`_real` default) carried a divergent, older form of the ckpt-key shim fix. Fixed
in place during the run with user approval (backup
`trainer.py.bak-20260816-121850`), but auto-retry had already exhausted its
attempts, so both slots stayed dead for this run.

Worth noting both slots ALSO hit `std::bad_alloc` on attempt 1 and *recovered*
from it -- the `Config.job` error is what actually killed them. Both surfaced as
the usual misleading `FAILOVER STOP: walltime`.

**Follow-up (2026-08-17).** t3 has since run to ~21k steps and finally has a
registered trajectory and a results page:
[2B-512 constant-LR fork](20260817-2b-512-constant-lr-fork.md). Short version:
holding LR constant from step-9200 tracks the decaying canonical chain within
+0.001 to +0.008 nats over ~12k steps, though the decay's payoff is expected
late and this covers less than half the run. t4 died again in the NEXT umbrella
(8756957) -- a *second* upstream key rename, `output.weight` -> `lm_head.weight`,
distinct from the qkv one; see
[the dispatch log](../../../../production/dispatch-log.md#t4-2b-256-constlr-has-failed-on-a-key-rename-three-times).

**2. t0's token budget was 2.96x too large.** It launched with
`--training.steps=70176` = 7.06T tokens of dolmino, against an intended 2.39T.
`TRAIN_TOKENS=7064155541716` was copied from MDS where it is the *cumulative*
budget through stage 2, but stage 2 writes to a new dir so its counter starts at
zero and `steps = tok/(gbs*seq_len)` has no notion of tokens already spent.

```
7064155541716 / (12288*8192) = 70,176 steps = 7.06T   (what ran)
2390375382006 / (12288*8192) = 23,742 steps = 2.39T   (intended)
```

Harmless under constant LR -- the budget sets only the stopping point, not the
schedule shape -- so the 3,312 steps that ran are valid and step-3300 resumes
as-is. Fixed in `cc4e22cfa`. Caught only because the fresh-chain question was
asked; the warm start itself was correct.

## Three things worth following up

**1. `std::bad_alloc` now has partial evidence, but a confound.** Slot launches
were exactly 20s apart (`LAUNCH_STAGGER=20`), and failures landed on the last
two launched, with rank counts rising 73 -> 145:

| slot | launched | clone | bad_alloc ranks |
|---|---|---|---:|
| t0 | 00:01:54 | agpt-2b-v2 | 0 |
| t1 | 00:02:13 | agpt-20b-v2 | 0 |
| t2 | 00:02:33 | agpt-20b-n256 | 0 |
| t3 | 00:02:53 | **constlr-from9200** | **73** |
| t4 | 00:03:13 | **constlr-from9200** | **145** |

That fits cumulative CCL/KVS pressure. **But those same two slots are the only
pair sharing a clone directory**, so launch-order and clone-sharing are
confounded and this run cannot separate them. `LAUNCH_STAGGER=180` alone will
not settle it -- the next test should ALSO give the two constlr chains separate
clone dirs. Stack is unambiguous about the site:
`ccl_comm::create -> initXCCLComm -> ProcessGroupXCCL::barrier -> bad_alloc`.

**2. 20B-512 checkpoints cost ~21 minutes each.** Two saves measured at 1,279s
and 1,303s (6,144 shards). At a 100-step interval and ~47s/step that is roughly
5% of wall-clock spent writing. Compare 20B-256 at 388-390s for 3,072 shards.
Worth revisiting `CKPT_INTERVAL` for the 512N chain, or async staging.

**3. `IDLE_TIMEOUT` was never passed, so it ran at the 1800s default** -- the
value that SIGTERM'd a healthy 20B-512 mid-DCP-load in umbrella `8744247`. It
did not bite this time (max observed silence on a live slot was well inside the
limit), but it was armed the whole run. `8756957` carries 5400s.
