# SFT on gs138650 with the FULL tulu_math_uc_mix (big OpenMathInstruct-2)

**Date:** 2026-07-10
**Machine:** Sunspot
**Job:** 12470281 (32N, select=36 = 32 train + 4 spare)
**Purpose:** More SFT tokens. The completed 729-step SFT
(`checkpoint-729-hf`) trained fine, but only on the small metamathqa-swap mix
(~4.5B tokens). This run does a longer SFT on the SAME base
(`global_step138650`, vocab 256000) over the FULL `tulu_math_uc_mix` (tulu-3
0.65 + OpenMathInstruct-2 0.15 + ultrachat 0.20, ~93.1M rows, ~54B tokens),
1 epoch at production-equivalent GBS=6144.

## Why this base (gs138650, not the v2 256N step-92859 checkpoint)

The v2 base (vocab 256128) deterministically hit a **scale-only oneCCL
collective GPU fault** at 384 ranks (libccl.so backtrace, jobs
12470254/258/262). 1-tile and 2N runs on the v2 base are clean; the fault only
appears at 32N. Root-caused but unsolved -- see
[`memory/project_sft_v2_base_oom_badnode.md`]. `global_step138650` is the
checkpoint the completed 729-step SFT trained on and it ran clean at 32N, so
building on it sidesteps the v2 crash while we chase that separately.

## Why the full mix is now cheap (the vectorized-interleave payoff)

The full `tulu_math_uc_mix` used to be avoided because OpenMathInstruct-2's 14M
rows made HF `interleave_datasets` take ~90 min (pure-Python per-row index
loop) and blew the XPU oneCCL barrier at 384 ranks (jobs 12468348/371/398). Two
fixes removed that:

- **Vectorized interleave** (commit b5798f532): replaced the per-row Python loop
  with a numpy replay of the RNG draw stream. Bit-identical output, 4.8s vs
  ~90min at the 93M-row scale. Also submitted upstream as
  [huggingface/datasets#8318].
- **Pre-built on-disk cache** (job 12470278, 286 GB, hash `44608c8c15bd9714`):
  the 32N job does `Dataset.load_from_disk` in <60s -- no build, no Hub calls,
  no oneCCL barrier at scale.

Because the mix is a local on-disk cache (`load_from_disk`) and the script sets
`HF_HUB_OFFLINE=1`, this path has **zero HF 429 exposure** -- unlike streaming
`--dataloader.dataset=<hub/name>` paths, which have no rank-0 barrier and
re-probe the Hub `dataset_info` per rank (that is a separate, still-open issue
on the pretraining/blendcorpus path).

## Reliability

- `--auto-retry --spare-nodes auto --max-failover-retries 3`: select=36
  (32 active + 4 spare); a bad-node GPU fault swaps in a spare and resumes from
  the latest checkpoint. `--spare-nodes auto` is REQUIRED -- without it
  auto-retry has no spare to swap and dead-ends at
  `FAILOVER STOP: stuck_pre_training` (learned the hard way on 12470254/258).
- `CCL_ZE_CACHE_{GET,OPEN}_IPC_HANDLES_THRESHOLD=8000`: raises oneCCL's
  Level-Zero IPC-handle caches so they don't exhaust device memory in a
  collective memcpy over a long run (job 12470088 OOM'd at step ~248 without
  this).

## Attempt 1 (job 12470281): died in tokenization, not training

Launched 2026-07-10 on 36 nodes. Weights loaded clean (111/111 shards/rank, no
Qwen fallback), the `load_from_disk` mix cache loaded fine -- then it died at
~19 min. Root cause was NOT the v2-base oneCCL scale crash and NOT a bad node:

```
Tokenizing train dataset (num_proc=32): 3%|3| 2818002/93144311 [17:29<8:48:03, 2850 ex/s]
[auto-retry] FAILOVER STOP: walltime (rc=143, attempt 1)
```

**SFTTrainer re-tokenizes+packs the WHOLE train dataset in `__init__` at job
start** (~2.5k ex/s at num_proc=32), so the 93M-row mix has an ~8.5h ETA before
step 1. That is longer than the auto-retry idle-watchdog tolerance, so the
watchdog SIGTERM'd the job (rc=143). The `oneCCL allreduce_scaleout ...
atl_comm->wait` exceptions and `rank N died from signal 15` lines in the log are
**teardown noise from the SIGTERM**, not a compute fault -- an easy misread
given the superficial resemblance to the v2-base crash.

Why the smokes missed it: the 2N smoke used `--max_train_samples 50000`, which
truncates BEFORE tokenize; the prior completed 729-step SFT used the tiny
metamathqa-swap mix (~100x fewer rows). Solving the interleave build (the
vectorized-interleave + cache work) just moved the bottleneck downstream from
interleave to tokenize.

## Fix: offline pre-tokenize (mirrors the interleave pre-build)

TRL 1.5.1 skips its tokenize+pack prep when the dataset already has an
`input_ids` column (`is_processed = "input_ids" in column_names`). So we move
the one-time tokenize cost into a dedicated 1N job, exactly as we did for the
interleave build:

- `train_sft.py` gains `--pretokenize_to <dir>` (build + run TRL prep once via
  SFTTrainer, save `trainer.train_dataset` with `input_ids`, exit) and
  `--pretokenized_dataset <dir>` (load_from_disk, hand to SFTTrainer, prep
  skipped). Saving the trainer's OWN processed dataset guarantees the offline
  result is bit-identical to in-process prep. Commit e6a92faf4.
- [`rl/scripts/sft/_pretokenize_tulu_math_uc_mix_1n.sh`](../../../../../rl/scripts/sft/_pretokenize_tulu_math_uc_mix_1n.sh):
  1N/12h, num_proc=96, single rank (no collectives / no watchdog). Writes
  `~/.cache/ezpz_sft_mixes/tokenized/tulu_math_uc_mix-gs138650-len2048`.
- The 32N script now loads that via `--pretokenized_dataset` (<60s to step 1).
- [`rl/scripts/sft/_smoke_pretokenize_roundtrip_1n.sh`](../../../../../rl/scripts/sft/_smoke_pretokenize_roundtrip_1n.sh):
  validates the round-trip on a 50k-row slice before the multi-hour full job.

### Round-trip smoke caught a second bug (assistant_only_loss guard)

The pre-tokenize round-trip smoke (job 12470282) passed phase 1 (50k rows ->
12,166 packed sequences with `input_ids`, `completion_mask`, `assistant_masks`,
`seq_lengths`) but phase 2 hit:

```
ValueError: You set `assistant_only_loss=True`, but the dataset is not conversational.
```

TRL `SFTTrainer.__init__` (1.5.1, line 380) runs
`is_conversational(dataset_sample)` even on the already-processed path; a
pre-tokenized dataset (`input_ids` + `assistant_masks`, no `messages` column)
is not "conversational" by that check, so the guard raises. But verified in TRL
source that the flag is safe to drop here: the collator applies `assistant_masks`
on PRESENCE alone (no flag dependency), and `compute_loss`/`training_step` never
reference the flag. The assistant-only masking is already BAKED IN as the
`assistant_masks` column during `--pretokenize_to` (where the flag is True).

Fix (commit eac2b135c): when `--pretokenized_dataset` carries `assistant_masks`,
`train_sft.py` sets `assistant_only_loss=False` to skip the spurious guard --
masking is preserved via the baked-in column. Warns loudly if masks are absent
instead of silently training on all tokens. Confirmed by the phase-2-only smoke
(job 12470283): 5 steps, loss 2.43 -> 1.49, grad_norm settled 680 -> 7.7,
`mean_token_accuracy` ~0.55 -> 0.65, no guard error, no re-tokenize.

## The save saga (jobs 12470284 / 12470322 / 12470323)

Getting the pre-tokenized dataset to disk took THREE save approaches -- the
tokenize map was cached throughout (reloads in ~1 min), so only the save was
ever redone:

1. **12470284** -- plain single-threaded `save_to_disk`: `trainer.train_dataset`
   is an indices-mapping dataset (`concatenate.select(idx)`), so save first does
   a slow single-threaded gather of the scattered indices over the ~369GB source
   (~17 MB/s on Lustre) before writing shards. It busted the 12h walltime at
   792/2639 shards (no manifest -> unusable partial).
2. **12470322** -- `flatten_indices(num_proc=96)` before save: the flatten runs a
   `map` that materializes large in-memory batches across 96 workers over the
   whole dataset -> a worker OOM'd ("subprocess abruptly died during map").
3. **12470323** -- `save_to_disk(num_proc=16)`, NO pre-flatten (commit
   38ffdd5d8): each writer gathers its shard incrementally bounded by
   `max_shard_size` (500MB), so peak RAM is ~16*shard, not the whole dataset.
   COMPLETED: 2,639 shards + manifest, 1.2T, 33.5M packed sequences at len2048.

## seq_len 2048 OOM'd the XPU tile (jobs 12470325 / 12470328)

With the 2048 dataset saved, training reached `Starting SFT training` (the
pre-tokenize skip + a `packing=False` fix both worked -- see below) then OOM'd at
step 0 in `compute_loss`: `level_zero backend failed with error: 40
(UR_RESULT_ERROR_OUT_OF_RESOURCES)`. Packing makes every sequence a dense
full-length block, so seq_len 2048 ~doubled activation memory vs the completed
SFT's 1024; bsz=1 + AC (via `fsdp_config`) were already maxed, so no free knob
remained at 2048. Reverted to **seq_len 1024, bsz=2/gas=8** (GBS held at 6144) --
the exact corner the completed 729-step SFT ran clean (commit 7d203e18d).

### A third bug the 2048 run exposed: TRL re-packs pre-packed data

Job 12470325 died `Bus error (core dumped)` during "Packing train dataset" at
92% -- TRL RE-PACKED the already-packed dataset. In
`SFTTrainer._prepare_dataset` the `if packing:` block is NOT under the
`if not is_processed:` guard, so skip-prep skips only TOKENIZATION, not packing.
Fix (commit deeacef0d): when the pre-tokenized dataset already has `seq_lengths`,
`train_sft.py` sets `packing=False` -- the data is already packed and the
collator keys off the baked-in columns.

## Re-tokenize at 1024: the packing num_proc walkdown

The 1024 re-tokenize needs a fresh tokenize map (different fingerprint than
2048). 1024 packs ~2x more rows (~53M vs 33.5M), and the parallel **packing**
map crashed a worker ("subprocess abruptly died") -- NOT node OOM (RSS
30GB/512GB), NOT disk/shm: pyarrow/multiprocessing flakiness at ~53M packed
rows. Progress scaled inversely with `dataset_num_proc`, so we walked it down
(env `NPROC` override, commit 7c82c6772):

| num_proc | packing outcome |
|---:|---|
| 96 | died @ 49% |
| 32 | died @ 86% |
| **8** | **100% -- succeeded** |

**12470334** (NPROC=8) completed: packing 100% (53,276,203 seqs) -> the
no-pre-flatten parallel save (2,160 shards + manifest, 1006G) ->
`PRE-TOKENIZE done`.

## BLOCKED: 384-rank GPU page fault at step 1-2 (scale fault, unsolved)

Every 32N attempt (jobs 12470336 / 12470338 / 12470339 + the drained afterany
chain) died at step 1-2 with a GPU page fault:

```
Segmentation fault from GPU at 0x... ctx_id: 5 (CCS) type: 0 (NotPresent), access: 1 (Write), banned: 1, aborting
-> rank 221 died from signal 6 (SIGABRT, core dumped)
```

Diagnosis (all evidence-based, no guessing):
- **Not a bad node.** Reproduces on rank 221 across DIFFERENT nodes
  (x1921c4s0b0n0 AND x1922c2s3b0n0); each afterany link gets a fresh PBS
  allocation yet the fault follows the rank.
- **Not an OOV token id.** Full columnar scan of all 53,276,203 rows (2160
  shards) -> global max token id 255998 < base vocab 256000. Ruled out.
- **It is a 384-RANK SCALE FAULT.** The 2N diagnostic
  ([`_diag_bigmix_2n_len1024.sh`](../../../../../rl/scripts/sft/_diag_bigmix_2n_len1024.sh),
  job 12470343) ran the SAME len1024 pretokenized dataset + SAME bsz2/gas8 at 24
  ranks for 20 steps CLEAN (loss 1.25 -> 1.12, mean_token_accuracy ~0.70,
  "Training complete", no fault). Identical data+config trains at 24 ranks,
  GPU-faults at 384. This is the
  [`project_sft_v2_base_oom_badnode`](../../../../../..) scale-fault class, and it
  is BASE-INDEPENDENT (moving v2-base -> gs138650 did not dodge it). The
  completed small-metamathqa 729-step SFT dodged it by luck, not because 384
  ranks is safe.
- **Also fixed en route:** ezpz `--auto-retry` false-positives on the TRL SFT
  path -- it detects progress via `step=N` markers, but TRL emits `{'loss':...}`
  dicts, so it declares `FAILOVER STOP: stuck_pre_training` after 2 crashes even
  though training stepped. Dropped `--auto-retry`; fault tolerance now via the
  afterany chain + `--resume_from_checkpoint` + save_steps=50 (commit f7c736bc9).
