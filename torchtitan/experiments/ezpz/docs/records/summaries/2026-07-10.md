## 1. Vectorized interleave -- the mix build, ~90 min -> ~5s

The registered `tulu_math_uc_mix` (tulu-3 0.65 + OpenMathInstruct-2 0.15 +
ultrachat 0.20, `all_exhausted`) materializes to ~93.1M rows. HF
`interleave_datasets` built the ~93M-element index in a **pure-Python per-row
loop** (~90 min), and at 384 ranks that build blew the XPU oneCCL barrier
(jobs 12468348/371/398) -- which is why the big mix had been avoided in favor of
a tiny metamathqa swap (~4.5B tokens).

- **Fix** (`b5798f532`): `_interleave_all_exhausted_fast` replays the RNG draw
  stream in numpy (`rng.choice` in 1000-blocks) and computes each source's stop
  position via `np.flatnonzero` -- **bit-identical** output for a fixed seed,
  **4.8s vs ~90 min** at the real 93M-row scale. A cached self-check
  (`_fast_interleave_matches_stock`) guards against a future `datasets` RNG
  change silently diverging.
- **Empty-row filter moved pre-interleave** (`e34325e26` -> `370e2c7fc`): the
  post-interleave filter scanned all 93M rows (~7h, busted a walltime, job
  12470276); filtering per-source *before* interleave is ~6x less work.
- **Cache pre-built** (`558b66765`, job 12470278): 286 GB, hash
  `44608c8c15bd9714`, so the training job does `load_from_disk` in <60s.

## 2. Offline pre-tokenize -- the SECOND bottleneck

Solving the interleave build just moved the bottleneck downstream. TRL
`SFTTrainer` **re-tokenizes+packs the whole train dataset in `__init__`** at
every job start (~2.5k ex/s), so 93M rows has an ~8.5h ETA before step 1. At
32N (job 12470281) that blew the auto-retry idle-watchdog, which SIGTERM'd the
job (rc=143) at ~19 min -- and the oneCCL `allreduce_scaleout` errors in that
log were **teardown noise from the SIGTERM**, not a compute fault. The 2N smoke
missed it because `--max_train_samples 50000` truncates before tokenize.

- **Fix** (`e6a92faf4`, `bb4480b33`): `--pretokenize_to` builds + runs TRL prep
  once (via SFTTrainer), saves `trainer.train_dataset` (with `input_ids`) to
  disk, exits; `--pretokenized_dataset` loads it and TRL skips prep (confirmed
  in 1.5.1: `is_processed = "input_ids" in column_names`). Saving the trainer's
  own processed dataset makes offline prep bit-identical to in-process.
- **Round-trip smoke caught a 2nd bug** (`eac2b135c`): TRL's `assistant_only_loss`
  runs an `is_conversational` guard even on the processed path; a pre-tokenized
  dataset (`input_ids` + `assistant_masks`, no `messages`) fails it. Verified in
  TRL source that the collator applies `assistant_masks` on *presence* alone
  (no flag dependency), so the fix auto-disables the flag when masks are baked
  in -- masking preserved, guard skipped, warns loudly if masks absent.
- **Validated**: phase-1 (50k rows -> 12,166 packed seqs) + phase-2-only smoke
  (job 12470283, loss 2.43 -> 1.49, grad_norm 680 -> 7.7, no re-tokenize).
- Full 1N pre-tokenize of all 93M rows (job 12470284, num_proc=96) run offline
  on a compute node; packing ~4.1:1 -> ~22-23M sequences.

## 3. The big-mix SFT run

- **Base: `global_step138650`** (vocab 256000), the checkpoint the completed
  729-step SFT trained on -- runs clean at 32N, so it sidesteps the v2-base
  oneCCL scale crash (Section 4). Script `3beb8f60e`.
- **Sizing**: seq_len 2048 (vs the prior SFT's 1024), 1 epoch (~54B tokens),
  GBS held at 6144 via bsz=1/gas=16 so per-device token load matches the prior
  2x1024. `--save_steps 200`, all ckpts kept, `--auto-retry --spare-nodes auto`.
- Loads the pre-tokenized dataset -> <60s to step 1, zero HF 429 exposure.

## 4. Upstream `datasets` PR #8318

The vectorized-interleave fix is also an upstream inconsistency: the
`probabilities=None` `all_exhausted` branch in `_interleave_map_style_datasets`
is *already* vectorized; only the `probabilities`-given branch fell back to the
per-row loop. Verified no existing issue/PR covers this (the 3 "interleave slow"
issues are all iterable/streaming, a different path). PR vectorizes both
probabilities-given strategies, bit-identical across seeds, with a benchmark
note (~90 min -> ~5s at 93M rows). Copilot review addressed (empty-source
`ValueError`, declined the argsort suggestion with benchmark data:
`flatnonzero` is faster).

## 5. v2-base 32N oneCCL scale crash (root-caused, unsolved)

The first big-mix SFT target was the completed v2 256N base (step-92,859, vocab
256128). At 32N it deterministically hit a **scale-only oneCCL collective GPU
fault** (libccl.so backtrace) across jobs 12470254/258/262 -- NOT a bad node,
data, tokens, or model issue (1-tile + 2N all run clean on the same base). Two
earlier red herrings ruled out first: an oneCCL IPC-handle-cache OOM (FIXED via
`CCL_ZE_CACHE_{GET,OPEN}_IPC_HANDLES_THRESHOLD`, `ff71b3e79`) and a missing
`--spare-nodes auto` (`3d4238029`). The scale fault itself is unsolved;
operationally sidestepped by building on gs138650 instead. Repro kept
(`6d2e2d181`).

## 6. HF 429 root-cause (streaming dataloader)

Separate from SFT: `--dataloader.dataset=allenai/olmo-mix-1124` 429-storms at
384 ranks because (a) the `HuggingFaceTextDataset` path never reaches the
`_rank0_prefetch_then_barrier` guard (guard is only in `datasets.py`'s
`_make_loader`), and (b) with `streaming=True`, `load_dataset` re-resolves the
revision online per call regardless -- no `HF_HUB_OFFLINE` is set on the
pretraining scripts (the SFT scripts all set it, which is why SFT never 429s).
Fix options: pin an explicit `revision=`, or `HF_HUB_OFFLINE=1` after a rank-0
warm. Documented for follow-up; does not affect the SFT run (on-disk cache).
