## 1. Data mix A/B -- 2026-07-28 to 08-08

> [!NOTE]
> The LR schedule is not the lever; the data mix is, enormously. 75% math / 25% edu is the sweet spot.

The cleanest scientific result of the window, and it was pre-registered:
held-out val loss (NLL) on frozen holdouts **disjoint from every training arm**,
~1600 steps / ~10B tokens per arm, from MDS `global_step138650`.

- **Does the LR schedule matter? No.** Constant-LR beats WSD-decay-to-zero on
  *both* bases. At 10B tokens the schedule is not the lever.
- **Does the data mix matter? Enormously.** Pure edu-web forgets math
  catastrophically; **75% math / 25% edu** keeps essentially all the math while
  capturing essentially all of edu's general-domain gain.

Follow-on arms (Phase 2 weighted owm/edu blends, Wave 3 science-corpus, a 90/10
math-heavy arm) were built on that finding.

**Wave 3 closed at the end of the window, and it is a clean negative.** Swapping
the 25% diversity corpus from fineweb-edu to cosmopedia-SCIENCE was supposed to
move the science holdout without giving back the math gains. It does neither:

| arm | FineMath | wikitext | peS2o |
|-----|----------|----------|-------|
| owm-100 (control) | **1.8039** | 2.6828 | -- |
| **owm75/edu25** | 1.8089 | 2.6597 | **2.1469** |
| owm50/edu50 | 1.8155 | 2.6519 | -- |
| owm75/cosmo25 (W3) | 1.8237 | **2.6471** | 2.1486 |

peS2o moves **+0.0017** -- indistinguishable from zero -- while FineMath costs
**+0.0148**, ~9x larger and worse on math than *every* Wave 2 arm including
50/50 past the knee. A strictly bad trade, so **owm75/edu25 remains the
recommended mix**. The one positive: cosmo takes the wikitext crown outright
(2.6471, beating even edu-100), consistent with general gains coming cheaply
from any diversity corpus -- edu just buys them cheaper.

What the data cannot settle: whether flat peS2o means 25% cosmo is too dilute at
10B tokens, or that peS2o (real papers) is too far from cosmopedia (synthetic
textbook prose) for transfer. The latter is likelier given +0.0017 is pure
noise, but that is a hypothesis.

## 2. MMLU flatline -- 2026-08-05

> [!NOTE]
> MMLU sits at the 4-way chance floor on every checkpoint, and the harness is clean -- so it is the data.

MMLU never leaves the 4-way chance floor on *any* AuroraGPT checkpoint:

| model | tokens | MMLU |
|---|---|---|
| 20B-256 | 0.39T | 0.2599 |
| 20B-512 | 0.71T | 0.2655 |
| 2B-512 | 3.99T | 0.2473 |
| 2B-256 **complete** | 4.674T | 0.2437 |
| 2B MDS dolmino | **7.06T** | **0.2413** |

No upward trend -- the most-trained model scores lowest -- while the same
checkpoints improve monotonically on everything else (HellaSwag 0.405 -> 0.561
across the completed 2B run). Eliminated in order:

- **tokens**: a COMPLETED 4.674T run finished at chance.
- **scale**: 7.06T with our best-ever ARC-C (0.3968) is still 0.2413.
- **tokenizer**: gemma-7b assets against gemma-tokenized data; the 256128 vs
  256000 vocab gap is 128-alignment padding.
- **the harness** (job 8736838): three cached public models through the exact
  same `simple_evaluate(num_fewshot=5, device="xpu:0")` path --
  **Llama-3.2-1B = 0.3121** (published ~0.32), **Llama-3.1-8B = 0.6530**
  (published ~0.66).

A 1B model clears chance on this path; our 2B at 7.06T does not. What is left is
the mix: `olmo-mix-1124` appears to carry little multiple-choice academic
content. **MMLU-style performance needs a data intervention, not more tokens.**

Two corrections landed here. The probed checkpoint is **7.064T on
dolmino-mix-1124-fused**, not 7.77T -- `ntok7770B` in the directory name is a
naming-convention target, and W&B reports `consumed_train_tokens =
7,064,147,460,096` at that step. And `eval_mds_sweep.sh` had never run MMLU on

## 3. ARC-C retraction -- 2026-08-05

> [!NOTE]
> The reported ARC-C decline was a shot-count key collision, not a real regression. Retracted.

Mid-window I reported ARC-Challenge falling 0.4138 -> 0.2875 toward chance and
wrote it into the journal as real. It is not. `arc_challenge` is scored **twice
per step** -- 0-shot in the commonsense block, 25-shot in the modern block --
and both wrote the same `arc_challenge` key, so the stored value depended on
which phase finished last. lm-eval's `n-shot` block was being dropped, leaving
nothing to disambiguate.

The driver now writes `<task>@<N>shot` alongside the bare key and preserves
`n-shot`. The first fully-namespaced evals show the artifact directly, on both
chains independently:

```
256n   arcC@0 ~0.350-0.368    arcC@25 ~0.268-0.288   gap ~7pp
512n   arcC@0 ~0.345-0.369    arcC@25 ~0.254-0.278   gap ~9pp
```

Both series are individually flat. Every pre-fix `arc_challenge` number in the
project is ambiguous.

> The ~2098N umbrella seated twice and carried all three chains; `std::bad_alloc` at init keeps eating whole trainer slots.

The ~2098N multi-chain umbrella finally seated after ~6 days queued (8714502,
8h01m) and again for a full 24h (8714503), carrying 2B-512 to 43,820, 20B-256 to
8,334, and 20B-512 to 7,654. A third (8744245) is mid-run.

Two structural findings:

- The summary banner reports `failed: 5/5` on **exit code**, so trainers that
  ran productively for hours and were then SIGTERM'd are indistinguishable from
  ones that never started. The [dispatch log](../../production/dispatch-log.md)
  now records what each slot actually did.
- **Three different failure modes all print `FAILOVER STOP: walltime`**,
  including a trainer that died 29 minutes into a 24-hour job. This actively
  slows triage.

`std::bad_alloc` at init is the open one: 6 slots across 3 umbrellas, landing in
`set_determinism` -> `broadcast(seed_tensor)` (the known 1024N crash function)
and in CCL `pmrt_kvs_get` bootstrap (the known KVS timeout). `LAUNCH_STAGGER=20`
puts **24,576 ranks** -- twice the documented single-job wall -- into bootstrap
inside 80 seconds, and in 8744245 three trainers died in a 25-second window right
after the last launch. But the same config produced three *different* outcomes
across runs, so it is filed as **open, not root-caused**, with a falsifiable next
test (`qsub -v LAUNCH_STAGGER=180`, ~1% of a 24h job).

Both fork slots had failed silently for three dispatches. They turned out to be
two unrelated bugs:

- **trainer 3**: "latest" resolved to `step-9260`, an aborted 24-entry partial

## 8. B-series SFT -- 2026-08-04

> [!NOTE]
> Teaching CoT in two stages beats one combined run by 3-10x; the sequencing matters more than the mix.

The B-series asked whether the GSM8K-CoT cold start could be rebuilt as a single
combined SFT run. It cannot, and the gap is not marginal:

| model | cot_accuracy | format | mean_gen_len | n_unclosed |
|-------|--------------|--------|--------------|------------|
| **B2 (two-stage: tulu-math -> gsm8k-r1cot)** | **0.205** | 0.985 | 282 | ~0 |
| B3 (single SFT, broad mix @8192) | 0.05 | 0.86 | 601 | 26 |
| B4a (gsm8k-r1cot finish on B3 base) | 0.02 | 0.26 | 1378 | 133 |
| B4b (reweighted + len-filtered @4096) | 0.065 | 0.86 | 611 | 27 |

Every single-stage rebuild lands at 0.02-0.065 against B2's 0.205 -- so the
*sequencing* matters more than the mix, filtering, or sequence length. B4b is
the sharpest datapoint: it fixed the run-on symptom the guardrails flagged
(gen_len 611, unclosed 27, format 0.86) and accuracy still barely moved, proving
verbosity was a symptom and not the cause. **~0.2 is near the 2B ceiling** --
across SFT recipe tuning and RL (flat 0.205 -> 0.215) nothing beat B2, so the
next lever is a bigger or math-pretrained base, not more recipe search.

## 9. PP + provenance -- 2026-08-05 to 08-10

> [!NOTE]
> The PP failure was a torch version floor, not a bug (PR retracted), and a holdout-provenance trap nearly invalidated a cross-wave comparison.

**PP is blocked by a torch version floor, not a bug.** `ValueError: Expecting N
arg_mbs but got 1` traced to `trainer.py` passing pre-split microbatch lists to
`pp_schedule.step()`. I opened a torchtitan PR against that -- and **retracted
it**: upstream `step()` now accepts `arg_mbs`/`kwarg_mbs` directly, so the call
site is correct and every torch we have simply predates the change. Gate before
attempting PP anywhere:

```python
"arg_mbs" in inspect.signature(PipelineScheduleSingle.step).parameters
```

Two lessons worth keeping. I checked pytorch `main` before filing a `fork_rng`
issue -- which correctly prevented a redundant report, since it was already
fixed -- and then did not apply that same check to my own patch. And upstream
runs PP integration tests in 8-GPU CI, so a universally broken PP path would
have been red; I explained that away as "a 5-day-old regression nobody noticed"
rather than treating it as evidence against my own diagnosis.

**Holdout provenance was a live silent-failure risk.** `eval/holdouts/` was
untracked scratch and got cleaned between Wave 2 and Wave 3. The sidecar meta
records dataset/config/split/num_docs but **not the HF revision**, so a rebuild
could not be verified by metadata -- and a resampling difference would have made
the Wave 3 delta meaningless while looking entirely plausible. Validated
empirically instead (re-scoring `owm75-edu25/step-1600` reproduced FineMath
1.8089 and wikitext 2.6597 exactly), then fingerprinted so it cannot recur:
`MANIFEST.sha256` (sha256 + line count + byte size, `sha256sum -c` verifiable).
The jsonls stay untracked -- 85 MB against a repo whose largest tracked file is
4.6 MB, with no git-lfs.

**A note on scoring cost.** The Wave 3 training ran first try; *scoring* took
five submissions (arg style, output parsing, model flavor, config vocab,
tokenizer). Every one was an interface guessed rather than read, and a
`2>/dev/null` in my own helper hid the real errors for two of those rounds.

## 10. Bad node -- 2026-08-05 to 08-10

> [!NOTE]
> Sunspot `x1921c4s3b0n0` is missing a project mount; every job that lands on it dies in about a second.

`x1921c4s3b0n0` carries **2** tegu mounts where healthy nodes carry 3, so the
project path is invisible there. Every rank placed on it exits 127 with
`Couldn't change directory to <repo>` -- and because one bad rank aborts the
whole MPI job, a single node takes down an N-node allocation in ~1 second.

It failed **5 of 5** appearances and never passed (jobs 12472558, 12472560,
12472573; `mounts=2` measured directly in 12472561; excluded as unhealthy by the
probe in 12472563). Other nodes in the same rack are fine, so it is node-local.

The failure gives no filesystem-level error -- just a failed `chdir` -- so it
reads as an application bug; several allocations were lost before probing mounts
directly. Working scripts now request N+1 nodes and drop any that cannot see the
repo, with the probe run from `/tmp` (from `$REPO` the chdir fails on the bad
node and tears down the probe itself, reporting zero healthy). That is a
workaround; an ALCF ticket is drafted.
