# 80B GBS=1488 512N-batch simulation (Sunspot, 2026-06-25)

Pushes the 80B TP=4/LBS=1/bf16 "stable corner" to **4x the validated
global batch** (GBS=372 -> 1488) by raising GAS, to simulate the global
batch an Aurora **512N** production run would see -- without leaving the
NaN-free `dp_degree <= 186` corner.

**Result: clean success.** 46/46 steps before the 4h walltime cut, zero
NaN, loss 12.92 -> 8.84. The stable corner holds at 4x batch.

## Why GAS, not more nodes

The 80B grad-path NaN has two independent triggers (see
`docs/production/agpt/80b/README.md`): `LBS > 1`, and large
`dp_degree = NGPUS/(TP*PP*CP)`. The safe corner is **LBS=1 AND
dp_degree <= ~186**. You reach a larger global batch by adding GAS
(sequential microbatches) -- which scales `GBS = dp_degree * LBS * GAS`
*without* touching `dp_degree` -- not by raising LBS or node count.

So to simulate the *global batch* of a 512N Aurora run while staying in
the safe corner, hold 62N (dp_degree=186) and set GAS=8:

| Quantity | This run | Aurora 512N (TP=4, GAS=1) |
|---|---|---|
| dp_degree | 186 | 1536 (would NaN -- 8x over ceiling) |
| GAS | 8 | 1 |
| **GBS** | **1488** | **1536** (~3% larger) |

GBS=1488 is within ~3% of the Aurora 512N global batch (1536), so the
optimizer sees a representative batch size, while dp_degree stays pinned
at the validated 186. This is a *batch-size* simulation, not a
node-count simulation -- it does **not** exercise the >512N init path or
the dp_degree>186 grad regime (both still open).

## Significance

The TP=4/LBS=1/bf16 corner was previously validated only at GBS=372
(100 steps, 12469551). This run shows it also holds at **GBS=1488 (4x)**,
i.e. the corner's stability is not specific to the small batch -- it
survives the global batch an Aurora 512N run would use. Combined with the
GBS=372 100-step run, the corner is the production-ready 80B path at both
the native (372) and 512N-equivalent (1488) batch scales, on the safe
side of the dp_degree<=186 ceiling.

What this does **not** establish: that the corner survives
`dp_degree > 186` (the actual 512N+ regime, where dp itself is the
trigger), nor the >512N distributed-init path (open `set_determinism`
crash at 12,288+ ranks). Those require a node-count study, not a batch
study -- see the dp-degree cliff bisect plan.

## Root cause of the multi-attempt arc (the real lesson)

This run was the **successful relaunch** after two prior allocations hung
in `config.build()` (dataloader/distributed init), ~20 min each, then
aborted. The whole arc traced to a **self-inflicted** barrier:

- I had added a global `torch.distributed.barrier()` inside blendcorpus
  `_build_index_mappings` (commit `c7eb628`), thinking it would close the
  TP>1 cache build-then-load race.
- **That function is called a data-dependent number of times** -- once
  per corpus x per split, with a `build_indices` branch that differs
  across ranks. So ranks reached the barrier a *mismatched* number of
  times, producing a classic partial-participation collective deadlock:
  `oneCCL allreduce_scaleout ... atl_comm->wait fails with status: 1`.
- **Reverted in `74b09fd`** (replaced with a NOTE explaining why no
  barrier belongs there). The relaunch (this job) then trained clean.

Misdiagnoses ruled out along the way:

- **NOT node health.** An `rc=127` on one attempt was a red herring
  (failover scrape noise); healthy nodes hung identically.
- **NOT batch size.** Step 1 was always clean on every attempt that
  reached training; the hang was in init, before step 1, independent of
  GAS/GBS.

The **3 sibling barriers** added in `debfff5` (`_cache_indices`,
`build_corpus_datasets`, `blendable_dataset.py`) are **correct and kept**
-- each sits next to a pre-existing collective and is reached uniformly
by all ranks. Only the `_build_index_mappings` one was wrong, because of
its data-dependent call multiplicity. (See blendcorpus PR #8.)

## Notes

- Lesson logged for systematic-debugging: a barrier is only safe where
  *every* rank provably reaches it the *same* number of times. Adding one
  inside a per-corpus/per-split, branch-gated function violates that.
- `VALIDATOR_ENABLE=0` was set because enabling the validator at 80B
  TP=4 hits a *separate*, still-open CCL collective deadlock (works at
  TP=1 debug; deadlocks at TP=4/62N). That is tracked independently and
  was deliberately sidestepped here so the batch-size question could be
  answered in isolation.
- Native `submit_agpt_80b_autoretry.sh` worked end to end: 62 active /
  6 spare split, `--np=744`, yeet, attempt 1 reached training with no
  bad-node swaps; the run ended by walltime cut at step 46 (step 47 would
  have needed ~305 s more, past the 4h cap).
