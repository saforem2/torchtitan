# 80B 512N production run NaN'd: SophiaG unstable at production batch

- **Date:** run 2026-07-03 (job 8574385), analyzed 2026-07-06
- **Machine:** Aurora
- **Status:** FAILED (NaN). First real 80B v2 production run to *place and
  execute* -- but it diverged to NaN by step 14 and ran NaN for the full 12h
  walltime. No usable training.

## What happened

The 80B 512N head (8574385) finally cleared the queue and ran a full 12h
window (Exit_status -29 = walltime). But it produced **no usable training**:

- Config: **SophiaG LR=1e-6**, warmup=4650, `decay_ratio=0` (constant),
  GBS=6120, TP=4/LBS=1, grad-clip `max_norm=1.0` (the base default).
- Loss was **flat at ~12.9** from step 1 (LR still ramping through the long
  warmup -- at step 14 LR ~= 1e-6 * 14/4650 ~= 3e-9, i.e. weights barely
  moving).
- **`grad_norm` -> `inf` at step 14**, `nan` at step 17, loss `nan` at step 18.
- It then logged NaN every step (tps ~35, glacial) from step ~18 to step 173
  where PBS killed it at walltime. ~12h of allocation, zero progress.

```
step: 12  loss: 12.94604  grad_norm:  6.1718
step: 13  loss: 13.01916  grad_norm:  6.1908
step: 14  loss: 13.05946  grad_norm:     inf   <- explodes
step: 17  loss: 12.93456  grad_norm:     nan
step: 18  loss:      nan  grad_norm:     nan   <- dead for the next ~155 steps
```

## Why longer warmup / grad clipping won't fix it

Two mitigations were **already in place** and did not help:

1. **Warmup was already very long (4650 steps).** At the NaN onset (step 14)
   the LR was ~3e-9 -- effectively zero. The loss was flat, so the divergence
   is *not* from update magnitude being too large. A longer warmup only makes
   LR smaller while the instability persists.
2. **Grad clipping was already active** (`max_norm=1.0`, applied in
   `trainer.py:707`). `grad_norm` still went to `inf`. Clipping the *gradient*
   norm cannot help when the overflow is **inside the optimizer step** --
   SophiaG's second-order Hessian (`grad*grad`) term overflowing bf16 at
   dim=9216. The reported `grad_norm=inf` is the clip routine seeing an
   already-non-finite gradient/Hessian.

This is the documented "SophiaG narrow band at production batch" fragility,
now confirmed at the 512N production dp-degree with a real long warmup: the
[80B convergence run (2026-06-30)](../sunspot/2026-06-30-80b-convergence-gbs6144.md)
found **all three optimizers NaN at their finder-recommended constant LRs**
(mano @ 3e-6 step 5, AdamW @ 5e-7 step 9, SophiaG @ 1e-6 step 12) -- a shared
instability at this corner. Our production run adds the data point that a
4650-step warmup does not rescue SophiaG.

## Next step: mano at a lower LR (probe first)

Per the LR-finder, **mano** is the safest-behaved optimizer at this batch in
the *sweep* -- but @ 3e-6 constant it died fastest (step 5). So the next
attempt is **mano at a lower LR (1e-6)**, well below its NaN edge, with the
200-step warmup and constant LR.

Rather than burn another 512N/12h allocation on a guess, this is being
**probed at small scale first**: job **8647404**, 32N, **GBS=6144** held via
GAS=64 (dp_degree=96, under the 186 NaN threshold), mano @ 1e-6, warmup=200,
constant, 40 steps (debug-scaling). Decisive question: does it survive past
step ~12 (where the whole class died) and descend? If yes -> candidate for a
512N production relaunch. If it also NaNs -> the shared Hessian/bf16 overflow
at this corner needs a root-cause fix (optimizer dtype/eps at dim=9216)
before any 80B production run is viable.

## Cost note

The failed run occupied 512 nodes for ~12h producing only NaN -- a ~6,100
node-hour loss. The auto-retry did not (and should not) catch this: it is not
a bad-node event, it is a deterministic numerical divergence, which no
node-swap can fix. **Guardrail idea:** a NaN-abort (kill the run on N
consecutive non-finite losses) would reclaim ~11.9h of the wasted window --
worth adding to the trainer, since a NaN'd 80B run currently burns its entire
walltime.
