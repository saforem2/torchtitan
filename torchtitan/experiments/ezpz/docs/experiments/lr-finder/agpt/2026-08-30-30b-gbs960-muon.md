## READ THE MUON NUMBER DIFFERENTLY -- verified on this exact config

Three facts separate the Muon suggestion from the other three arms. All were
measured against `agpt_30b_olmo2tok_muon` by building the model on meta and
applying the optimizer's own gate, not derived from the source by reading.

### 1. Only 21.5% of the model is actually on the Muon path

Muon partitions **by tensor shape, not by name**
(`torchtitan/experiments/ezpz/optimizer/muon.py:85-89`, again at `176-179`):

```python
use_muon = p.ndim == 2 and max(p.shape) <= 10000
```

Anything failing that test falls through to an internal AdamW branch, silently.
At 30B (dim=6144, hidden_dim=16384, vocab=100352) that splits as:

| path | tensors | params | share | which |
|---|---:|---:|---:|---|
| **Muon** | 256 | 5.637B | **21.5%** | all four attention projections, x64 layers each: `wq` (6144,6144), `wo` (6144,6144), `wk` (1024,6144), `wv` (1024,6144) |
| AdamW | 323 | 20.561B | **78.5%** | `w1`/`w3` (16384,6144) x64 each, `w2` (6144,16384) x64, `tok_embeddings` + `lm_head` (100352,6144), 129 rank-1 norms |

So **this arm is a Muon/AdamW hybrid, not a Muon run.** The wide FFN matrices
that dominate the parameter count sit on the AdamW side, as do the embedding
and head. That is a property of the implementation, not a choice made for this
experiment -- but it means "Muon at 30B" should be written as "Muon on
attention projections, AdamW on everything else" wherever the result is cited.

The split falls on a real architectural line: **every attention projection is
on Muon, every FFN matrix and both embedding-sized tensors are on AdamW.** The
gate is nominally about shape, but at this flavor it separates attention from
MLP exactly. That is a coincidence of dim=6144 and hidden_dim=16384 straddling
the hardcoded 10000, not a designed boundary -- at a flavor where `dim`
exceeded 10000 the attention projections would silently move to AdamW as well,
and the arm would become a pure-AdamW run wearing a Muon label.

### 2. The suggestion is a BASE lr; Muon tensors see 15.677x it

For Muon-path tensors the lr is rescaled per tensor by
`0.2 * sqrt(max(A, B))` (`muon.py:130-139`, applied at `230-231`). The finder
sweeps and records `param_group["lr"]` (`lr_finder.py:143` and `195`) -- the
base, before that rescale.

All four Muon-path shapes have max dim 6144 -- (6144,6144) for `wq`/`wo`,
(1024,6144) for `wk`/`wv` -- so the factor is **uniform**:

```
0.2 * sqrt(6144) = 15.677
```

This corrects an expectation worth stating plainly: the factor is NOT
shape-dependent at this model size, and the frequently-quoted 25.60x for
(6144,16384) **never applies**, because those `w2` tensors fail the `<= 10000`
gate and are on the AdamW path. There are exactly two effective learning rates
in this run:

| path | effective lr |
|---|---|
| Muon tensors (21.5% of params) | 15.677 x suggested |
| AdamW tensors (78.5% of params) | 1.0 x suggested |

So if the finder returns `S`, report it as: **base `S`, effective `15.677*S` on
attention projections.** Compared against the other three arms -- whose
suggestions are effective lrs directly -- the base number alone understates
Muon's real step size on the tensors it governs by more than an order of
magnitude.

### 3. bf16 does NOT overflow at this dim -- verified, and the docstring's threshold did not reproduce

`muon.py:14-38` warns that at dim >= 9216, bf16 overflows in `A @ A` at NS step
~7 and fp32 at ~16, concluding "Muon is not currently viable for 80B dense
models." At 30B the Muon-path shapes are (6144,6144) and (1024,6144), below
that threshold, and the run is safe. Measured with `ns_steps=5`
(`containers.py:381`, `default_muon`'s value), tracking `max|A@A|` per iteration
against the bf16 ceiling of 3.3895e+38:

| shape | on Muon path | peak `\|A@A\|` | result |
|---|---|---:|---|
| (6144,6144) `wq` | yes | 0.9102 | finite |
| (1024,6144) `wk` | yes | 1.0469 | finite |
| (16384,6144) `w1` | no | 1.2031 | finite |
| (9216,9216) | n/a | 0.8672 | finite |

Peak magnitudes sit near 1.0, roughly 38 orders of magnitude below the bf16
ceiling. **bf16 overflow is not a risk for this run.**

Two caveats on that, both flagged rather than resolved:

* The docstring's own danger case **did not reproduce**. (9216,9216) stayed
  finite at `ns_steps=5`, and (6144,6144) stayed finite out to `ns_steps=24`
  (peak 1.1094). The NS iteration normalizes `X` by its spectral norm before
  iterating, which is what keeps `A @ A` near unity. The warning may be
  specific to a condition this synthetic-Gaussian probe does not reproduce
  (real gradient spectra, a different ns_steps, or accumulated momentum). Treat
  the 80B claim as unverified here rather than refuted -- this run does not
  test it.
* The probe ran on CPU with synthetic Gaussian input. Real XPU gradients could
  differ; the margin (38 orders of magnitude) is large enough that this is
  noted for completeness, not as a live concern.

### 4. `adjust_lr_fn` is NOT selectable for this optimizer

The `original` / `match_rms_adamw` / `spectral_unclamped` choice lives at
`torchtitan/distributed/flex_shard/dist_muon.py:1810-1824` -- a **different,
upstream** Muon implementation that this arm does not use. The ezpz Muon
(`experiments/ezpz/optimizer/muon.py`) has no such parameter. Its only lever is
the boolean `adjuster_lr_ref` (`muon.py:56`, `230-233`):

| `adjuster_lr_ref` | method | ratio |
|---|---|---|
| `True` (ezpz `Muon` default, `muon.py:56`) | `adjust_lr_for_muon` | `0.2*sqrt(max(A,B))` = **15.677x here** |
| `False` (`MuonClip` default, `muon.py:364`) | `adjust_lr_for_muonclip` | `max(1, A/B)**0.5` |

`default_muon` (`containers.py:371-390`) does not pass `adjuster_lr_ref`, so
this run takes the `True` default and the 15.677x factor above. Worth noting
the equivalence: ezpz's `True` branch is the same formula upstream calls
`match_rms_adamw`, and its `False` branch is upstream's `original`. So this run
is on the RMS-matching variant, and it is not configurable from the config
registry without adding a kwarg.

## Protocol -- identical to the three 2026-08-23 arms

```bash
qsub -v OPT=muon -N lrf-muon lrfind_opt.pbs      # -> 12474326
```

Same parameterized script the other three used, extended with a fourth `case`
arm rather than copied. Sweep and batch:

| | value |
|---|---|
| sweep | 1e-6 -> 1e-1, exponential |
| steps | 100 (`training.steps=1000` x `fraction=0.1`) |
| warmup | `warmup_fraction=0.1` -> 10 steps held at init_lr |
| smoothing | `smooth_frac=0.1`, EMA beta 0.98 |
| batch | GBS=960 = LBS 5 x 192 ranks x GAS 1, seq 4096 -> 3.93M tok/step |
| data | fineweb-edu local parquet, via `_use_fineweb_edu` |
| TP | 1 |
| checkpoints | disabled (`--checkpoint.no-enable`) |

Verified by parsing the flag list **extracted from `lrfind_opt.pbs` itself**
(not retyped) through the real `ConfigManager`, single-process, before
submitting: `GBS=960, GAS=1.0, LBS=5`, `checkpoint.enable=False`,
`optimizer=Muon`, `dataloader=GrainDataLoader.Config`.

The upper bound must bracket a real blow-up. A sweep that never diverges
produces **no suggestion at all** -- the finder warns and returns nothing.

## The launch found a stale flag that would have killed all four arms

`lrfind_opt.pbs` passed `--dataloader.num-workers=2`. That parsed on
2026-08-23 and does not parse now:

```
Unrecognized options: --dataloader.num-workers=2
```

`#4088` replaced the dataloader with Grain and `#4121` landed after those runs.
`GrainDataLoader.Config` (`torchtitan/components/data/loader.py:57-73`) has no
`num_workers` field -- its nearest equivalent is `num_prefetch_batches`, which
is `tyro.conf.Suppress`ed and not settable from the CLI. The old pre-Grain
dataloader had it; the dumped config from job 12473714 shows
`"num_workers": 2` under a `"dataloader_type": "single"` block that no longer
exists.

`optcmp.pbs` already dropped the flag when Phase 2 hit this exact class of
failure, but `lrfind_opt.pbs` had not been rerun since 2026-08-23 and was
stale **for all four arms, not just muon**. The flag is now removed, with the
reason recorded in the script.

This is the fifth instance of the documented parse-time failure cascade, and
it is why the preflight parses the flags **extracted from the script** rather
than a hand-copied list: a retyped list can pass while the script still holds
a flag that aborts the job 47 seconds in.

## The figure would have dropped this arm silently

`scripts/plot_lrfind_30b.py` hardcoded its own three-arm list (`ARMS`, line 54)
separately from the config registry and the PBS script. Regenerating the figure
after this sweep would have rendered the **same three curves**, written the SVG,
and exited 0 -- registering a config and a PBS arm is not enough to reach the
chart.

Two fixes, both verified by rendering to a scratch directory rather than
trusting the exit code:

1. **`muon` added to `ARMS`** with its own color (`#9467bd`) and `None` for the
   suggestion, so the curve plots before the number is known. The dotted
   suggestion line is skipped rather than drawn at a guessed value. Dry run
   prints `muon: NO CSV -- skipped` and produces a 3-color SVG today; when the
   CSV lands, `#9467bd` appearing in the SVG is the check that the arm actually
   reached the figure.
2. **The zoom panel's x-window is now derived from the data.** It was hardcoded
   `1e-5 .. 3e-3`, which fits arms whose minima cluster at 3-6e-04. Muon reports
   a BASE lr that its 15.677x rescale shifts left, so a minimum at or below
   4e-06 would have fallen off the left edge -- invisible, figure still saved,
   exit 0:

   | muon min | old window | new window |
   |---|---|---|
   | 3.0e-05 | visible | visible |
   | 4.0e-06 | **CLIPPED** | visible |
   | 2.0e-06 | **CLIPPED** | visible |

   With no low arm present the derived window reproduces the old one, so the
   three existing curves are unchanged.

Caveat: the dotted suggestion line for Muon, once filled in, is a BASE lr and
is **not** like-for-like with the other three arms' lines. That is noted in the
script next to the value.

## What to look for

1. **Did it blow up?** No blow-up means no suggestion and the sweep must be
   rerun with a higher `max_lr`. Check `blow-up at` in the PBS stdout.
2. **`GAS reported: 1`** in the summary block. Anything else means the batch
   moved and the result is not comparable to the other three arms.
3. **`"optimizer_name": "Muon"`** -- confirms the arm ran the optimizer it
   claims.
4. **90 rows in the CSV**, each with `global_batch_size=960, world_size=192`.
   Check the CSV, not the log summary; this is what makes the arms comparable.
5. **Where the suggestion lands.** The other three cluster in 3.05-5.61e-05
   (within 1.8x). Muon's base could reasonably land ~15x lower if the
   rescale dominates, which would put it near 2-4e-06 -- that would be the
   rescale showing up, NOT Muon being a fundamentally different optimizer.
   Compare `15.677 * base` against the other three before concluding anything
   about relative step size.
6. **`rc=124`** means the inner timeout fired and the sweep did not finish;
   treat the result as incomplete rather than reading a partial curve.

## If the suggestion is used for a Phase 2 Muon arm

Pass the **base** lr to `--optimizer.param-groups.0.optimizer-kwargs.lr`, the
same flag `optcmp.pbs` already uses -- the 15.677x is applied internally by the
optimizer and must NOT be pre-multiplied. Pre-multiplying would run the
attention projections at 246x the intended lr.

A Phase 2 Muon arm would also need its own `case` entry in `optcmp.pbs`
(currently `adamw|mano|sophiag`); that has not been added.
