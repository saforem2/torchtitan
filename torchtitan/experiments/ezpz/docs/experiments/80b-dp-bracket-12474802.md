# dp=192 vs dp=96: the cleanest single-variable test in this investigation

**Running as `12474802`.** Written before the outcome.

## The matched pair

Searching the archive for failures at *reachable* scale turned up
`8540102` (2026-06-12), recorded in
[`20260611-80b-n32-nan-diagnosis.md`](agpt/aurora/20260611-80b-n32-nan-diagnosis.md)
rather than in the canonical NaN doc:

> Job 8540102, n=64, GBS=384, `--debug.seed=42 --debug.deterministic`.
> Training: loss 12.92 -> 12.41 across steps 1-8 (clean), then **grad_norm =
> nan at step 9** -> **loss = nan at step 10**, NaN persisted through step 20.
> No node failure. Earlier signal: grad_norm = `inf` at step 3, the clip
> kicked in, loss spiked 12.86 -> 13.28, and the model recovered for 5 more
> steps before the second overflow at step 9 finished it.

Set that beside last night's `12474768`:

| | nodes | **dp** | GBS | seed | outcome |
|---|-------|--------|-----|------|---------|
| `8540102` | 64 | **192** | 384 seqs | 42 | inf@3, **NaN@9**, dead by 10 |
| `12474768` | 32 | **96** | 384 seqs | 42 | **40/40 clean, zero non-finite** |

Same batch. Same seed. Same model. The material difference is dp.

## Why this is the right run

Everything else has been excluded or is held fixed:

- **LR trajectory alone**: excluded. `12474765` ran 25/25 clean at
  `8574385`'s effective LR at every step (matched to 9 significant figures).
- **GBS at dp=96**: excluded. Two arms 16x apart in batch agree on means to
  0.03-0.20% while variances scale on `sqrt(16)` exactly as sampling
  predicts.
- **Optimizer, seed, model, host quality**: held constant.

So dp is the last variable standing, and this is the first time it has been
testable -- 64 nodes were unobtainable for most of the previous session.

## Cost

`8540102` died at step 9, and a GBS=384 step costs ~2 min (measured on
`12474768`). 20 steps is ~40 min plus ~35 min init. A 4h wall is generous.
This is a **75-minute** experiment, not a 14-hour one.

## Pre-registered reading

**If it goes non-finite at or near step 9:** dp is the variable, the bracket
is 96 (safe) to 192 (fails), and the capture instrumentation fires on a real
event for the first time -- naming the tensor. That would be the strongest
result available from this machine.

**If it stays clean through 20 steps:** dp=192 alone does not break a
configuration that is clean at dp=96 *at this LR*. Note this run keeps the
rescaled trajectory (peak `5.376344e-09`, warmup 25) rather than
`8540102`'s `agpt()` default, so the two differ in LR as well as nothing
else. A clean result would therefore promote **the LR** back to prime
suspect and the obvious follow-up is this exact configuration at the
original's default LR.

**Either way** the run is decisive about something, which is why it is worth
64 nodes for 75 minutes.

## What it will NOT establish

It does not reproduce `8540102` -- the LR differs, deliberately, to keep it
comparable to its dp=96 twin. It does not speak to dp~1530 (`8574385`'s
scale), and it cannot separate dp from what changes *with* dp: reduction tree
shape, accumulation order across more ranks, and FSDP shard size per rank.
Those are a bundle at fixed node count and would need a further design to
tease apart.

## A near-miss worth recording

I first targeted `8673658` (64N, dp=192, NaN ~step 37) as the reproduction
config. It is `agpt_80b_fp32res_depth` -- fp32 residual across all 84 layers,
an intervention run -- not stock `agpt_80b`. Checking the config before
building on it avoided a baseline that was never a baseline.
