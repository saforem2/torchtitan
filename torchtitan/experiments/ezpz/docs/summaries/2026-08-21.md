## Headline

**The proposed 30B went from a design document with no config to a measured,
tuned, scaled model in one day.** Best config so far is **28.99% MFU at 2N**
(128k vocab, LBS=4); with the production gemma vocab it is **27.89%**. It
holds **25.54% at 64N**, decaying **1.42% per doubling against the 2B's
13.96%** -- the first real evidence for the 30B-exp proposal's central claim.

Along the way several things the docs asserted turned out to be wrong, most of
them written by me earlier in the same campaign -- all recorded in §5.

## 1. The 30B trains, and batch size is the lever

`agpt_configs["30B"]` did not exist until this week -- `30b-exp/` was a
proposal whose performance claims could not be tested. Added by interpolating
the family (the proposal fixes only `dim=6144`): dim 6144, 64 layers, 48
heads, 8 kv, ffn 16384, head_dim 128 matching both neighbours. 28.1B params.

Tuning at 2N ([exp05](../production/agpt/30b-exp/exp05-2n-performance.md),
jobs `12473195`-`12473197`):

| config | tps/GPU | MFU | memory |
|---|---:|---:|---|
| uncompiled, LBS=1 | 340 | 20.35% | 73.0% |
| compiled, LBS=1 | 360 | 21.54% | 68.1% |
| compiled, LBS=2 | 434 | 25.99% | 80.6% |
| **compiled, LBS=3** | **466** | **27.89%** | **78.5%** |

**Tensor parallelism hurts monotonically** -- TP=2 costs 26%, TP=4 costs 55%.
The model fits at 2N without it, so there is no memory reason to pay.

**LBS=3 is faster *and* cheaper in memory than LBS=2** (78.5% vs 80.6%).
Larger batches amortize the activation peak better, so "bigger batch = more
memory" does not hold across that step.

**Activation checkpointing is not optional**: `ac=none` is a genuine OOM
(746 MiB requested, 126 MiB free).

## 2. Scaling: 8x better decay than the 2B

[exp06](../production/agpt/30b-exp/exp06-scaling.md), job `12473198`, 64 nodes:

| nodes | ranks | tps/GPU | MFU | vs 2N |
|---:|---:|---:|---:|---:|
| 2 | 24 | 458 | 27.45% | 100% |
| 4 | 48 | 451 | 27.03% | 98.5% |
| 8 | 96 | 443 | 26.53% | 96.7% |
| 16 | 192 | 445 | 26.67% | 97.2% |
| 32 | 384 | 440 | 26.36% | 96.1% |
| 64 | 768 | 426 | 25.54% | 93.0% |

**1.42% MFU lost per doubling, against the 2B's 13.96%.** Flat within 1.9
points across a 32x scale-up, no cliff. (The ladder's own 2N point is 458 tps
/ 27.45%, slightly under exp05's 466 / 27.89% for the same config -- a ~1.6%
run-to-run difference, at the edge of the measured noise floor. Ratios above
use the ladder's own 2N so every point comes from one job.)

Two caveats recorded in the doc rather than buried:

- **64N is three doublings short of 512N**, and the 2B's collapse was a cliff,
  not a slope. Extrapolation through smooth terrain cannot locate a cliff.
- **At 64N the 2B itself still runs 25.9%** -- nearly identical to the 30B's
  25.54%. The measured range does not yet separate the two models; it shows
  the 30B does not degrade *earlier*, which is necessary but not sufficient.

**A constraint the proposal omits:** LBS=3 held to 512N implies **GBS 18,432
sequences, 75M tokens/step**. The 2B already measured a batch ceiling *below*
that -- at GBS=12,288 it lost 3-8pp on lm-eval per token against GBS=6,144,
with per-step parity confirming the architecture was fine. So the MFU argument
and the batch ceiling point in opposite directions, and only the first is
argued.

## 3. Tokenizer: there is no 64k, and 128k wins on memory (not on MFU directly)

All agpt models inherit **gemma-7b, vocab 256,128**. At dim=6144 that is
**3.15B params, 11.2% of the model** in the embedding.

The proposal asks for "~64k custom BPE". Nothing on hand is 64k -- vendored
are gemma (256k), Llama-3.1/3.2 (128k), llama-2 (32k) -- so it would mean
training one. `agpt_30b_llama3tok` uses the 128k Llama-3 vocab as the closest
existing option (embedding 3.15B -> 1.58B, 26.5B total).

That config **had never produced a single step**, for two bugs both mine
(`4275bdb9b`): it inherited gemma's `hf_assets_path` while declaring
`vocab_size=128256` (a tokenizer that can emit ids the embedding cannot
index), and its docstring instructed `--tokenizer.path`, which is not a flag.
Every run died in argument parsing, invisibly, because the harness never
created the log file.

Fixed, at matched settings:

| | params | LBS | tps | MFU | memory |
|---|---:|---:|---:|---:|---|
| gemma 256k | 28.1B | 2 | 434 | 25.99% | 80.63% |
| Llama-3 128k | 26.5B | 2 | 449 | 26.17% | 61.75% |
| gemma 256k | 28.1B | 3 | 466 | 27.89% | 78.50% |
| Llama-3 128k | 26.5B | 3 | 480 | 27.98% | 67.35% |

**In MFU this is a tie** (+0.09pp at LBS=3, inside the <1% noise floor). MFU
already normalizes by each model's own FLOPs, so a smaller model gets no free
bump; the +3.0% tps is just less model to push. Both variants gain the same
~1.85pp from LBS 2->3.

**The freed HBM does buy a batch step gemma cannot reach** (job `12473202`):

| | LBS | tps | MFU | memory |
|---|---:|---:|---:|---|
| gemma 256k (best) | 3 | 466 | 27.89% | 78.50% |
| **Llama-3 128k (best)** | **4** | **497** | **28.99%** | **75.98%** |

Best-vs-best that is **+6.7% tps and +1.10pp MFU**. Unlike the matched-LBS
comparison, this one is *not* explained by the smaller parameter count --
MFU is FLOP-normalized, so the gain is genuine per-GPU efficiency bought with
the extra batch step. gemma is already at 78.5% at LBS=3 and cannot follow.

So the tokenizer choice is worth ~1.1pp of MFU, but only *via* the memory it
frees, and only because batch size is the dominant lever on this model.

## 4. HSDP fails on the 30B, and it is not an OOM

Both HSDP attempts died with `UR_RESULT_ERROR_OUT_OF_RESOURCES`, which I
recorded twice as an out-of-memory. The traceback says otherwise:

```
trainer.py:819  clip_grad_norm_ -> clip_grad.py:106
                torch.stack([norm.to(first_device) for norm in norms])
RuntimeError: level_zero backend failed with error: 40
```

It failed at **71.68% memory with 18 GiB free**, in gradient clipping, after a
full step. That is device-*resource* exhaustion (events, command lists), not
memory. The LBS=1 "give it more room" retry failed identically -- which should
have flagged the framing sooner.

Four arms (job `12473199`) settled it:

| arm | verdict |
|---|---|
| **20B + HSDP** | **works** -- 12/12 steps, 488 tps, 21.72% MFU |
| 30B + HSDP, `foreach=False` | fails, identical frame |
| 30B + HSDP, `max-norm=0` | fails (my test was broken -- see below) |
| 30B + HSDP control | fails |

**Model size is the axis.** I had argued the opposite: since it is not an OOM,
a smaller model should fail the same way. The 20B arm refutes that directly.
Treating one refuted mechanism (memory) as evidence against an unrelated
hypothesis (size) was the error.

**`foreach=True` is exonerated** -- the unfused path fails identically. Added
`EZPZ_CLIP_NO_FOREACH` (`74f17090d`, default unchanged) with one-time logging,
so the log proves which path ran instead of assuming the env var reached the
ranks. It did.

**Not tensor count either:** 20B and 30B both have 579 parameter tensors. Only
sizes differ (2,623M vs 3,147M largest), so the ceiling is per-allocation.

Bisect point would be `dim=5632` (~24B). But HSDP measured **21.72% MFU** on
the 20B against plain FSDP's **27.89%** on the 30B, so the guide's "+2.7% MFU,
prefer HSDP" ([exp03](../production/agpt/30b-exp/exp03-1b-proxy-design.md))
does not reproduce at this scale on XPU, and the prize may not justify the
nodes.

## 5. Mistakes worth keeping

- **"HSDP OOM'd", written twice.** See §4.
- **`--training.max-norm=0` does not bypass clipping.** `get_total_norm` runs
  unconditionally at `distributed/utils.py:651`; `max_norm` is only read by
  the scaling call at 675. That arm was a duplicate control.
- **`--tokenizer.path` is not a flag.** The field is top-level
  `hf_assets_path`. Cost every llama3tok run, silently.
- **Run-to-run noise is under 1%, not ~6%.** A round-2 control reproduced
  LBS=2 at 434 tps / 25.96% against 434 / 25.99%. The wrong assumption had
  caused a real +5.9% compile effect to be dismissed as noise.
- **`compile` defaults ON** in `agpt()`, so a "compile" arm was a no-op.
- **I called the 128k "the better config outright"** on a +3.0% tps reading,
  before checking that MFU is FLOP-normalized. It is a tie.
- **A `git stash pop` with nothing stashed** restored an unrelated 11-day-old
  autostash and conflicted a generated SVG. Undone without dropping the stash.
