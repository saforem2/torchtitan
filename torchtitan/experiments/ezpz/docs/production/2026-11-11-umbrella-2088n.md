## Summary

One 2088-node PBS job held four seats: 20B-512, 20B-256, agpt-v2 4B (512N) and
agpt-v2 10B (768N). It ran **4h26m** of 24h. PBS then killed the whole job
because one node in the 10B slice had a GPU fatal error. The two 20B seats and
the 4B were all training when it died.

## What went wrong

### 1. One node failure killed every seat

`x4415c5s5b0n0` hit `grf_fatal_singlesubslice_error` at 06:51 and PBS killed
the job at 07:02. The ezpz spares and the umbrella relaunch only help while the
job is alive. They do nothing when PBS ends the job. With four seats in one job,
any of 2088 nodes can take all four down.

**Fix:** one PBS job per seat.

### 2. 10B at 768N (9216 ranks) did not train

Three from-scratch attempts gave step-1 loss **17788**, **24202** and **38478**.
The same config logged 11.99 at 2N (`9055264`), and the 4B logged 12.00 at 512N.
After the bad step-1 losses, a barrier in `_set_pg_timeouts_xpu_aware` failed:

```
oneCCL: allreduce_scaleout_sycl.cpp:80 ... atl_comm->wait fails with status: 1
```

ezpz stopped with `FAILOVER STOP: deterministic_failure` after three identical
failures. The umbrella then relaunched the seat, which got stuck before training
(`stuck_pre_training`) on both later attempts.

Unverified inference: the oneCCL scale-out allreduce is broken at 9216 ranks on
this stack. It was not isolated further. The 1024N init crash from 2026-05 is a
similar scale ceiling.

**Fix:** 10B moved to 512N (6144 ranks, GBS 6144, `dp6144` manifest).

### 3. Every v2 rank contended for one HF datasets lock on `/home`

Each rank called `load_dataset` with the default cache under
`~/.cache/huggingface/datasets`, a single directory on `/home` shared by all
ranks. They all serialized on one lock file in `DatasetBuilder.__init__`.

- 4B (6144 ranks): ~6 min before step 1.
- 10B (9216 ranks): **~53 min** per attempt.

**Fix:** `HF_DATASETS_CACHE=/tmp/hf-datasets-<job>-seat<N>`. `/tmp` is separate
on each node, so only the 12 ranks on a node share a lock.

### 4. 20B-512 hung once and is slow

It hung after step `10854` at 04:12. The watchdog killed it at 05:13, and ezpz
restarted from `step-10800`. Loading that checkpoint takes 682-735s. The 81
steps lost to the hang were never checkpointed, so none of its progress
survived. Throughput:

| Seat | tps/GPU | MFU | s/step |
| --- | ---: | ---: | ---: |
| 20B-512 | 278 | 13.9% | ~60 |
| 20B-256 | 328 | 16.4% | ~60 |
| 4B 512N | 781 | 8.5% | ~5 |

The cause of the hang is not known. Nothing in the resubmission changes it.

### 5. Monitoring gap

The job died at 07:02. The agent watching it noticed at ~15:10, about 8h later.
Its watcher had exited at 06:20, when the 10B was relaunched, and was not
restarted while it waited for Sam's answer on the 10B. Its stall rule had also
been raised from 15 to 40 min to sit through the 10B lock wait, so it stayed
quiet through the three failed 10B attempts. The new watcher restarts after
every wake and saves what it has already seen, so it never re-reports old news.

### 6. The v2 manifests are sorted, which makes the mix a curriculum

Found 2026-11-12 during the PR review, not in a run. `build_olmo_mix_manifest.py`
wrote its file list sorted by path. HF `split_dataset_by_node` gives rank `r`
files `r, r + 6144, r + 12288, r + 18432`, and the streaming source does not
shuffle shards, so at any moment all 6144 ranks read one quarter of the sorted
list. Files per subset in each quarter of `olmo-mix-dp6144.txt` (file counts,
not tokens):

| Quarter | Sorted (`olmo-mix-dp6144.txt`) | Seed-0 shuffle (`olmo-mix-dp6144-shuf0.txt`) |
| --- | --- | --- |
| 1 | algebraic-stack 16, arxiv 20, dclm 6108 | dclm 5925, starcoder 201, 18 others |
| 2 | dclm 6144 | dclm 5908, starcoder 214, 22 others |
| 3 | dclm 6144 | dclm 5896, starcoder 230, 18 others |
| 4 | dclm 5240, starcoder 863, pes2o 26, open-web-math 13, wiki 2 | dclm 5907, starcoder 218, 19 others |

With the sorted file, no rank sees code until its fourth file.

**Fix:** the builder now shuffles with a fixed seed by default (`--order
sorted` reproduces the old files). `olmo-mix-dp6144-shuf0.txt` is the same
24576 files as `olmo-mix-dp6144.txt` in seed-0 order, and is the 10B default
in `seat-autoretry-20261111.pbs`. The 4B stays on the sorted file: it resumes
from `step-2600`, and its data cursor indexes into that file order.

| 20B-256 | `9076346` | 260 | `small`, 12h | `step-21100` |

All four were `Q` at submission. They were submitted before the manifest fix
(item 6), so queued `9076371` still reads the sorted `olmo-mix-dp6144.txt`. To
start the 10B on the shuffled file, resubmit seat 4 with
`-v MULTI_ONLY=4,MANIFEST_V2_10B=/flare/AuroraGPT/foremans/scratch/umbrella-v2-manifests/olmo-mix-dp6144-shuf0.txt`
before it starts. Each seat resumes from the latest `step-*` in
its own checkpoint folder. The 20B
`BLENDCORPUS_RESUME_CONSUMED_SAMPLES` override (`15482880` / `10002432`) only
applies when a checkpoint has a missing or zero sample counter. `step-21100`
has a nonzero counter, so the 20B-256 does not rewind its data. See
[BlendCorpus resume-position analysis](../guides/blendcorpus-resume-position.md).

The `small` queue caps walltime at 12h for 256-1024 nodes. A 24h run now needs
two chained jobs per seat.
