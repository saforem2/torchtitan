# Production Training Metrics -- Ground-Truth Store

Committed, offline copies of the per-step training metrics for every
AuroraGPT production chain. This exists so plots, dashboards, and README
tables stop re-pulling ~92 W&B runs from the cloud on every refresh, and so
the data-provenance work in
[`trajectories.py`](../../../utils/trajectories.py) is captured once instead
of being rediscovered.

Generated by
[`utils/export_ground_truth.py`](../../../utils/export_ground_truth.py).

## Two tiers

The full store does not fit in a repo (measured 2026-08-17: **30.79 MB** raw,
13.17 MB gzipped, across 7 chains / 182,120 rows). So it is split:

| Tier | Location | Contents | Size |
| --- | --- | --- | --- |
| **Full** | `/flare/AuroraGPT/foremans/production-metrics/` (Aurora, outside git) | every step, every metric | 30.79 MB |
| **Summary** | this directory (committed) | all `olog` rows + a step-stride backbone | **1.61 MB** |

The summary is what you get in a checkout. It is enough to plot a loss curve,
sanity-check a chain's shape, and detect drift, with no flare mount and no
W&B credentials.

## What the summary keeps

Two rules, unioned:

1. **Every row whose `source` is `olog`**, at full fidelity, no decimation.
   These are the irreplaceable ones -- see below.
2. **A step-stride backbone of `wandb` rows**, with the stride picked per chain
   so each lands near 2,000 rows, plus the first and last step.

The stride applies to the step VALUE, not the row index, and snaps to a round
number. That keeps the selection stable as a live chain grows: step 4600 is in
the file whether the chain has 8,000 rows or 80,000, so a re-export **appends**
rather than rewriting every line.

**What that costs.** A chart is ~800-1600 px wide, so 2,000 points already
exceed what a full-width plot can resolve -- the summary curve is visually
indistinguishable from the full one. The cost is between samples: at these
strides (50 steps for the long 2B chains, 5 for the 20B ones) a transient
shorter than the stride -- a single-step loss spike, a one-off grad-norm
excursion -- can fall between samples and be invisible. **Anything hunting
short-lived anomalies must read the full store.**

## The `source` column

Every row is tagged `wandb` or `olog`.

- `wandb` -- came from the W&B API.
- `olog` -- recovered by parsing a PBS `.o` / console log.

This is not bookkeeping trivia. Roughly 16 of 18 runs on the 20B chains ended
`crashed`, and a crashed run never syncs its buffered tail, so its final steps
exist only in the job's stdout. For some steps **the log is the only surviving
record**: run-ids `oqqhoxz6`, `d00iszlc`, and `sn4q74lc` return `CommError`
from the W&B API today -- those runs were purged or never synced, and the
numbers would be gone entirely if the log had not been scraped.

That is exactly why the summary keeps every `olog` row uncompromised: 4,081
rows across the whole store, about 190 KB, and they are the part that cannot
be re-fetched from anywhere.

Provenance is derived structurally, not guessed: a W&B record carries all ten
metric columns (present even when null), a log-parsed record carries only the
six that a stdout line exposes. `--verify` cross-checks that inference against
a direct re-parse of every fallback file.

## Reading it

Column 1 is `_step`, so an anchored grep answers a point query:

```bash
grep '^4500,' torchtitan/experiments/ezpz/docs/production/metrics/20b_v2_256.csv
```

The header names every column; the loss is `loss_metrics/global_avg_loss`.
(Step 4500 is on the 20B chains' stride-5 backbone. On a 2B chain, a step off
the stride lives only in the full store.)

From Python:

```python
from torchtitan.experiments.ezpz.utils import export_ground_truth as gt

records = gt.load_summary("20b_v2_256")   # committed, always available
records = gt.load_chain("20b_v2_256")     # full fidelity, needs the flare store
manifest = gt.load_manifest()
```

Both return the same list-of-dicts shape as `wandb_fetch.concat_chain`, so a
consumer switches over by swapping the call and dropping its `wandb.Api()`.
A missing file **raises** rather than silently falling back to W&B -- a silent
fallback would reintroduce the credential-bound, non-reproducible fetch this
store exists to remove.

## `manifest.json`

Per chain: W&B run-ids used, `.o` fallbacks attached, step range, row count,
`wandb`/`olog` split, remaining gaps of 50+ steps, summary stride, and a
SHA-256 of both the full and summary files. Plus a top-level `exported_at`.

Use it to tell at a glance whether the store is current, and to check whether
a local full-store copy matches the export the summary came from.

## Regenerating

**Run on Aurora.** The `.o` and console-log fallbacks only exist on that
filesystem; an export from a laptop silently drops every recovered step and
quietly shrinks the chains.

```bash
cd /lus/flare/projects/AuroraGPT/foremans/projects/saforem2/torchtitan-ezpz
export http_proxy=http://proxy.alcf.anl.gov:3128
export https_proxy=http://proxy.alcf.anl.gov:3128
./.venv/bin/python3 torchtitan/experiments/ezpz/utils/export_ground_truth.py \
    --repo-root "$PWD" --verify
```

Takes about 8 minutes, dominated by W&B API paging over the long 2B chains.
`--verify` re-reads every written file and asserts it round-trips exactly, that
steps ascend, that every `olog` tag is backed by a real parseable log line, and
that no `olog` row was lost to decimation. Always pass it before committing.

## This is a SNAPSHOT

For a chain still training (`cls: live` in
[`trajectories.py`](../../../utils/trajectories.py)), the store lags by
however long ago the export ran. Check `exported_at` in the manifest before
treating a chain tip as current. The store is not a live feed and will not
update itself.

| `2b_v2_512_lr3.22e-5` | 200 | 1..200 | 0 | 200 / 1 | none |

`80b_v2_4_smoke` is skipped: it carries no W&B run-ids (a 4N validation smoke,
never a chart trajectory).

A gap means the record is missing, not that training stopped -- checkpoints
generally exist across these windows. The two 20B chains were audited and
closed in August 2026 (see the provenance notes in `trajectories.py`); the two
2B holes are **unaudited** and may well be closable by the same method: find
the `.o` or umbrella console log whose step range spans the hole and attach it
to the run that owns those steps. Do not interpolate across a gap.
